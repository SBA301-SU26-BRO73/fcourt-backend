# Proposed staff integration contracts

Version 1, SCRUM-26. Project owner approved adapters and boundary stubs until
owning services exist. These endpoints are proposals, not implementations on dev.

## Authentication

RS256 JWT via AUTH_JWK_SET_URI, exact issuer, configured audience (fcourt by
default), mandatory exp, positive numeric sub, roles array or scalar role.
IAM GET /api/auth/me authenticates forwarded Bearer and returns
`{"id":1,"role":"ADMIN","status":"ACTIVE"}`. Every operation rechecks activity;
IAM must revoke access after disablement. Tokens/credentials are never persisted.

## Facility

GET /api/admin/branches/{branchId} authenticates ADMIN, enforces ownership and
returns `{"id":7,"adminId":1,"status":"ACTIVE"}`. Deleted/inactive branches must
not be returned as ACTIVE. Adapter independently checks ID, owner and activity.

GET /api/staff/branches/{branchId} authenticates STAFF and returns
`{"id":7,"status":"ACTIVE"}`. Staff service verifies its local assignment first.
Facility must not synchronously call /api/staff/me in this lookup (would recurse);
use an agreed assignment projection/separate internal boundary if needed.

## IAM staff commands

Require caller ADMIN Bearer; IAM independently enforces target STAFF account
belongs to caller's owned branch. Arbitrary user ID is never authorization.

- POST /api/internal/staff-accounts: branchId, email, password, fullName, phone;
  provision ACTIVE STAFF with branch ownership metadata.
- PUT /api/internal/staff-accounts/{id}: branchId, fullName, phone; immutable
  branch/email and authorization checked server-side.
- DELETE /api/internal/staff-accounts/{id}: disable managed STAFF; resolve branch
  server-side. Return status INACTIVE, including idempotent replay.

All success responses must contain the account, not 204:

```json
{"id":100,"email":"staff@example.com","fullName":"Staff member","phone":"0912345678","role":"STAFF","status":"ACTIVE"}
```

Header `Idempotency-Key: staff:<actorId>:<UUID>` must have durable, concurrent-safe
replay scoped to authenticated actor. Reject different operation/target metadata
with same key. Same create key returns same account; first credential wins and
retry is not password reset. Never store plaintext passwords in replay records.
Keep replay records long enough for recovery after ambiguous local failures.

401/403/404/409 map to equivalent errors. Unexpected 4xx, 5xx, timeout or invalid
response maps to 503. Never expose raw upstream body. IAM success can precede
local rollback: retry exact key/request to recover, never silently use a new key.
No distributed transaction is claimed. Account provisioning, ownership, JWKS and
revocation must be tested against actual services before enabling real traffic.

## Booking operations — SCRUM-28

BOOKING_URL defaults to http://localhost:8088. All calls carry the STAFF Bearer;
booking must independently enforce branch assignment (projection/internal trust
contract, not client-controlled branch IDs).

GET /api/internal/branches/{id}/schedule?startDate=YYYY-MM-DD&endDate=YYYY-MM-DD
returns a bounded bulk read (including empty courts):

```json
{"branchId":7,"courts":[{"courtId":21,"courtName":"Court 1","slots":[{"bookingId":42,"date":"2030-01-01","slotStart":"09:00","slotEnd":"09:30","status":"CONFIRMED","customerName":"Guest","guestPhone":null}]}]}
```

At most 100 courts and 3360 rows per court; one entry per court/date/start.
Exclude superseded cancelled entries when another booking occupies that slot.
Times are same-day local times in configured STAFF_TIME_ZONE. Wrong branch,
out-of-range dates, malformed/duplicate IDs and unknown state fail closed.

POST /api/internal/bookings/check-in receives branchId, actorId, checkInCode,
date (business today), checkedInAt (UTC instant), channel (QR). Idempotency-Key
is staff:check-in:<actorId>:<UUID>. The authority must check account/assignment,
resolve the exact code within the branch, verify booking date, atomically compare
CONFIRMED and update CHECKED_IN + checkedInAt. New-key repeated check-in is 409;
same-key retry returns the original committed result even if state has advanced.
It must preserve request identity across retry even when caller timestamp changes.
Calendar date/timestamp are generated by staff, not client command identity:
replays after midnight return original result/date. New commands still require
today's booking date. Staff fingerprints exclude the generated date and accept
past committed results only with matching business date/checkedInAt.
Never blindly overwrite status from an event or trust caller actor/branch alone.

Response: bookingId, branchId, date, status CHECKED_IN, checkedInAt. Errors:
400 invalid code/request, 404 not found within branch, 409 wrong date/state or
already checked in. Booking authority performs atomicity across service instances;
the staff service never updates booking_db. Payment SCRUM-38's proposed QR payload
is the raw 32-digit checkInCode, compatible with the opaque code field here.
The API does not fetch URLs or log/retain raw QR codes.

Staff atomically stores a local command result and outbox after command success.
An ambiguous timeout/local failure requires the same client key to reconcile the
remote result. No automated progress is possible after permanent upstream loss;
never report a missing local event as successful delivery.

## Kafka delivery

KAFKA_BOOTSTRAP_SERVERS defaults localhost:9092; STAFF_EVENTS_TOPIC defaults
fcourt.staff.events. Outbox relay is enabled unless STAFF_EVENTS_ENABLED=false.
Envelope: eventId (stable UUID), type BookingCheckedInEvent, version 1, data
containing booking result, actorId, channel and occurredAt. Key is bookingId.
Booking and reporting consumers need separate consumer groups to both receive it.

The relay marks publication only after acknowledgement, retaining unacknowledged
rows on failure. An advisory transaction lock serializes relays; batches are 10.
Delivery is at least once: crash after acknowledgement before DB commit duplicates
the same event ID. Consumers must deduplicate eventId and must not regress booking
state if an older event arrives. Booking has already applied the guarded command;
event consumption must be idempotent, not a second unchecked status transition.
Retention, alerting for pending outbox age and production broker replication are
deployment responsibilities. End-to-end consumer processing is not yet verified.
